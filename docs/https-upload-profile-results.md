# 上传分段计时实测

本轮只增加计时，没有优化上传参数。成功文件的 71 次 PUT 中，92.93% 的设备请求时间落在 socket poll 等待；
服务端扣除等待接收请求体后的平均处理时间约 13.79 ms/片。后续应优先分析发送和响应等待链路，尚不能据此断言某个窗口或 ACK 配置就是根因。

## 样本与有效性

- 文件：`20261020172204:2`，1,158,663 字节，初始确认断点 0。
- SHA-256：`a3dd2b9269ec9374a08c9f4e67b9faeb2efd4bab833ac7725740137d9b09f634`，设备与服务器最终长度、哈希一致。
- 完整设备事件 77 条，顺序连续，无环形缓冲覆盖丢失；71 次 PUT 与服务器的对象摘要、偏移和长度逐条配对。
- 分片仍为 16 KiB，最后一片不足 16 KiB；TCP 窗口、缓冲、TLS 写入粒度、重试、超时、串行上传和持久确认规则均未调整。
- PUT 累计 190.134 s，有效负载速率 5.95 KiB/s；整次观测 206.12 s，含准备和联网的速率约 5.49 KiB/s。
- 计时为墙钟时间，包含调度和 USB 采集干扰；没有关闭计时的同文件完整传输对照，不能量化计时自身的开销。

测量镜像摘要：`cd180f369de1e6acfe1067167bf3f5d9bcde638f2d37481602d2ad25b244b48f`。
它基于 `9364e0e921a12e2257012b52da73d37ac907ce43` 的未提交快照 revision 2 编译，完整清单和差异保存在本地分析目录。
相对于当前批量版，配置仅增加 `CONFIG_CLIP_HTTPS_PROFILE=y`，签名文件路径随独立源码目录变化；SDK 版本、网络诊断生成源码、分区及外置 Wi-Fi 补丁均已核对。

本次开始前校时缓存有效，因此 clock 事件约 0.03 ms，不能把它当成一次 SNTP 联网校时的耗时。

请求体读取包含等待设备和网络到达，不能将 1.7 s 全部解释为服务器计算或磁盘处理。

## 失败样本与交叉验证

初版计时输出不兼容固件精简 printf 的 64 位格式，返回的 JSON 无法解析；已取消该测试，修正为本地整数转十进制，未改变全局格式化配置。
主机测试补充了精简格式约束，修正版实机事件流也验证了输出。

随后保留了两次开启计时和一次关闭计时的 TLS 握手超时，均没有传输文件负载。
开启计时的失败样本中，握手函数累计调用约 3–5 ms，等待读取接近 10 s。
关闭计时的失败连接，服务器收到 ClientHello 后发送了握手数据，389 字节尾部未获得确认并重传。

交叉验证中，此前的批量版镜像成功进入 HTTP；换回相同测量镜像重新启动后，关闭计时也成功进入传输，
随后开启计时完成了本报告的完整文件。因而不能将超时认定为测量镜像必现回归，也不能称其已经解决。
这些轮次受重启、地址及时序影响，不是随机抽样，不能据此计算稳定成功率；失败轮次与成功吞吐统计分开保存。

## 服务端 Nagle 对照定位

在相同计时镜像、同一设备和网络中，只切换服务端 accepted socket 的 `TCP_NODELAY`，做 A/B/A 对照。
每轮向隔离接收目录从零上传同一文件 `20261020080208:1`（574,179 B），保留 16 KiB 分片、串行持久确认和全部磁盘同步。
设备与服务器逐片按 offset、length 配对：三轮各 36 个成功 PUT、42 条连续事件，无计时覆盖丢失。
原目录及三个隔离目录的最终 SHA-256 均为 `d0dba2ec425ed469b4b5ab1f9b6e9b1786e3396b1575a03984eb10eb4074d018`。

| 指标 | A1：默认 Nagle | B1：TCP_NODELAY | A2 重试：恢复 Nagle |
| --- | ---: | ---: | ---: |
| PUT 累计时间 | 96.44 s | 79.96 s | 103.63 s |
| PUT 有效负载速率 | 5.81 KiB/s | 7.01 KiB/s | 5.41 KiB/s |
| 平均回执阶段 | 1238 ms | 900 ms | 1373 ms |
| 平均等待可写 | 1163 ms | 1145 ms | 1329 ms |
| 服务端平均非请求体处理时间 | 15.05 ms | 14.14 ms | 14.11 ms |
| 正文写入返回后仍有未发送字节 | 36/36 | 16/36 | 36/36 |

本表吞吐只用 PUT 累计时间，包含最后一个不足 16 KiB 的分片；不含准备、联网、TLS 和初始 GET。
初次 A2 的 USB 采集出现 `Device not configured`，观测不完整，未纳入上表；恢复 USB 后使用新的空目录重做整轮。
三轮先后进行，未随机交错，不宜据此承诺固定的提升比例或长期成功率。

### 已确认的贡献因素

接收端 `end_headers()` 和 `wfile.write(body)` 分别发送头和 JSON 正文。
诊断同时记录 accepted socket 的实际 `TCP_NODELAY` 值，以及每次 SSL sendall 前后的 TCP 输出队列字节数。
默认设置的两轮中，36 次正文均暂留在未发送队列；典型样本为头部对应 198 B TLS 数据已经发送但未确认，
随后正文对应的整个 154 B TLS 记录留在未发送队列。
关闭 Nagle 后，20/36 次正文写完即无未发送字节，平均回执阶段比 A1 减少约 339 ms；恢复后等待再次增加。
因此，分开发送小回执与 Nagle 是已确认的拖慢因素，服务端磁盘处理不是本轮秒级等待的主要来源。

队列使用 Linux `SIOCOUTQNSD`（仅未发送字节）和 `SIOCOUTQ`（未发送及未确认字节）区分，
不能把 outq 非零直接理解为尚未发送。定义见 [Linux socket ioctl 头文件](https://raw.githubusercontent.com/torvalds/linux/master/include/uapi/linux/sockios.h)。
这些调用只记录长度、时间和队列计数，不记录认证头或正文内容。

### 尚未定位完的部分

`TCP_NODELAY` 轮仍有 16/36 次正文暂留队列，且等待可写仍约 1.15 s/片。
因此不能声称关闭 Nagle 已解决整体慢速，也不能只凭队列计数把残留归因于拥塞窗口、接收窗口或重传。

实际构建配置为发送数据池 16,384 B、接收数据池 4096 B，最大 TCP 窗口配置均为 0。
匹配 SDK 的 `subsys/net/ip/tcp.c` 将默认最大窗口取数据池的三分之一：发送 5461 B，接收 1365 B；
排队长度受 `send_win - send_data_total` 限制，且拥塞初始窗口为 1 MSS。
这些限制与每片平均出现约 4–5 次 WANT_WRITE 相符，是下一轮单变量对照的候选原因；尚未通过窗口对照实测确认贡献大小。
下一步应固定服务端策略，只改变设备发送窗口，比较同一文件的等待可写、重传和内存占用，避免同时更改分片、TLS 粒度与缓冲。

本轮未刷机，未永久修改服务端配置。实验覆盖已移走，服务恢复原始启动参数且 active；设备 IDLE，自动上传和计时均关闭。
原始记录、无效 A2 样本、逐片配对分析脚本及汇总位于 `.analysis/https-runtime-0.1.2/tcp-wait-v1/`。
