# v0.1.2 运行时资源实测

测量版已刷入并启动。普通、增强录音与 BLE 下载通过；发现增强录音停止后
Wi-Fi AP 启动失败的可复现现象，重启后 AP 可以启动。尚未测试录音与网络传输并发。

## 镜像与方法

- 基线：`845713be7d595c0c7d40a16cab677a6ea74aa805`。
- 测量固件代码提交：`ecc10080b907326d9fb14bb960b1c4bf773e17f5`，
  分支 `experiment/runtime-resources-0.1.2`。后续采集脚本/报告提交不改变固件。
- 配置：Production + `applications/clip/runtime.conf`，应用版本仍为 `0.1.2`。
- 设备回读的 MCUboot 镜像哈希：
  `54bafa07d60fb7e44bb3a4810e90e21b15d0d1ebbb58820c522fdf3750b62a1c`。
- 签名 BIN SHA256：
  `4ed17e3c60256ab7625ef7ff3b7aed8748a72ebd66350a6549f12ad58bc6521a`。
- 仅刷应用；保留已有 bootloader、网络核、配对与录音。
- 全程 BLE 连接采样；USB 数据模式、SD 日志关闭。USB 线物理连接，电池满电，
  此测试不测电流或续航。空闲前等待 46 秒，CPU 采样后才扫描线程栈。
- CPU 来自调度器忙/闲计数差分，录音约每 3 秒查询一次；均值按区间时长加权。
  录音采样窗口约 30 秒，随后扫描栈，因此实际音频各约 32.24 秒。
- Wi-Fi AP 空闲数据来自另一次正常重启，Mac 未加入 AP，未进行 UDP/HTTPS 上传。

## 静态空间

| 应用资源 | 基线 | 测量版 | 增量 |
|---|---:|---:|---:|
| Flash / 933376 B | 930756 B | 932644 B | 1888 B |
| 静态 RAM / 450560 B | 430930 B | 432642 B | 1712 B |

Flash 使用率 99.92%，代码区剩 732 B。签名包大小 933492 B，加上镜像起始地址后，
距内部 LittleFS 起始边界仍有 396 B。签名验证与设备镜像哈希匹配通过。
静态 RAM 已含系统堆与静态线程栈，不能再与下面的堆使用量相加。
链接尾部约 17.5 KiB 由独立 libc malloc arena 使用，不能当成通用空闲 RAM。

## CPU 与系统堆

| 场景 | CPU 加权平均 | CPU 区间范围 | 系统堆当前分配 | 本次启动以来堆峰值 |
|---|---:|---:|---:|---:|
| BLE 连接空闲，6 个区间 | 0.07% | 0.07–0.09% | 1232 B | 1752 B |
| 普通录音，10 个区间 | 42.59% | 39.61–45.91% | 16472 B | 33384 B |
| 增强录音，10 个区间 | 71.07% | 64.92–79.53% | 51624 B | 68536 B |
| 重启后 AP 空闲，6 个区间 | 0.10% | 0.03–0.21% | 37456 B | 39536 B |

系统堆配置 81920 B，统计可分配区为 81824 B。增强录音的采样时剩余 30200 B，
历史分配峰值对应的余量只有约 13288 B。峰值是分配统计，不等同于当时最大连续块，
也不保证下一次大块分配一定成功。

这些统计不包含独立 libc allocator 和 Wi-Fi 专用控制/数据堆等专用池。
Opus 与 SpeexDSP 在此源码中使用自定义 `k_malloc` 适配，计入所测系统堆。
增强模式的 Opus 码率仍是 32000、复杂度仍为 1，不能将负载增量归因于更高码率。

## 录音与 BLE 下载

| 模式 | 会话 | 文件大小 | Opus 包数 | 成功解码时长 |
|---|---|---:|---:|---:|
| 普通 | 20261019034254 | 118206 B | 1612 | 32.24 s |
| 增强 | 20261019034329 | 87850 B | 1612 | 32.24 s |

两文件均通过传输序号、声明长度、文件末 CRC32 和 TRANSFER_DONE 文件数校验，
并完整解码。原有两个会话仍可列出。音频内容不进入 Git。
BLE 下载时 AT 通知存在延迟，CPU 计数时刻与主机收到响应的时刻不完全一致；
保留原始值，暂不将这些窗口汇总成稳定传输 CPU 占用。

## 已发现的限制与后续

1. 增强录音停止后系统堆仍分配约 51624 B。源码保留 Opus/SpeexDSP 实例以复用，
   停止录音不等于释放音频实例。随后 AP 启动连续两次返回
   `Failed to start WiFi AP`，失败后峰值为 80984 B，距统计可分配区仅 840 B。
2. 正常重启后，未开启录音，AP 能启动；堆当前分配 37456 B，峰值 39536 B。
   这是资源保留/容量问题的重要线索，尚未捕获分配失败的底层错误，
   不能直接定为唯一根因，也尚未与无测量开关的基线做同序列 A/B 对照。
3. 首次 AP 启动响应超过采集工具原来的 20 秒超时，重新连接后确认 AP 已运行。
   采集脚本已为 `AT+WIFI=on` 使用 60 秒超时；任何请求超时后必须重新连接。
4. Production 中 Wi-Fi 的默认编译日志级别为 0。临时打开 SD 日志未取得本次
   失败的底层详情，已恢复关闭。后续定位需有选择地保留错误日志，同时核算 Flash。
5. 录音与 Wi-Fi/HTTPS 并发、UDP 实际传输、长录、反复切换、掉电与续航均未验证。
   下一步先定位录音后保留的资源与 AP 启动需求，再决定修复和并发测试方案。

测试结束设备状态：IDLE、normal、AP 关闭、USB 数据模式关闭、SD 日志关闭。
设备继续运行此测量镜像，未升级 v0.1.4。
